# ADR-0004 · 境内 PostgreSQL：云托管优先 / 自建兜底，不用 Supabase

- 状态：已采纳
- 日期：2026-11-04
- 关联：ADR-0002（统一 Postgres）；`docs/database-architecture.md` §2 / §7

## 背景

ADR-0002 已定“生产统一 Postgres、不用 Supabase”，但落地形态此前只在“纯自建（CVM + 云盘）”与“Supabase”之间二选一。深审暴露出纯自建的真实短板：**备份 / PITR / 高可用 / 监控全要自己搭，而当前备份尚未自动化**——等于承担了自建的运维风险，却没拿到可靠性。同时 Supabase 的三个硬伤对本项目依旧成立：

1. **无中国大陆节点**：CN 用户跨境延迟约 150–300ms，且触发 PIPL 数据出境评估；彩票相关 + 境内用户场景下数据不出境是底线。
2. **Auth 不贴合中国**：内置手机认证走 Twilio 等，接腾讯云短信 / 微信强制绑手机很别扭；这套认证我们已自建。
3. **与现有栈冲突**：PostgREST / RLS / SDK 与既有 FastAPI + SQLAlchemy + Alembic + OpenAPI codegen 重复；用量成本随增长不可控。

还存在被忽略的第三条路：**云厂商托管 Postgres**（腾讯云数据库 PostgreSQL / TDSQL-C、阿里云 RDS PG）。它保留境内 + 标准 PG + 无 BaaS 锁定的全部优点，把备份 / PITR / 主备切换 / 监控交给云厂商，恰好补上纯自建的最大缺口。

## 决策

1. **首选云托管 Postgres**（腾讯云数据库 PostgreSQL / TDSQL-C）作为生产默认形态：境内节点、标准 PostgreSQL 16、自动备份 + 按时间点回档 + 主备切换。对单人 OPC、不想半夜处理备份 / 故障切换的场景，这是更稳的默认。
2. **纯自建作为低成本兜底**：预算极紧或需要完全控制（自定义扩展 / 参数）时使用；但**必须先落地 `database-architecture.md` §7 的备份 / PITR**，否则不允许上生产。
3. **不用 Supabase**：理由见背景；数据库代码保持标准 PostgreSQL，不写任何 Supabase / 云厂商专有 API。

**不变量**：无论云托管还是自建，都是标准 PostgreSQL 16；连接只走 `JQ_DATABASE_URL`，schema 只走 Alembic。**切换形态不改一行业务代码**（云托管 ↔ 自建只是换连接串 + 运维责任归属）。

## 后果

- 运维责任下降：备份 / PITR / 高可用由云厂商兜底（云托管形态），或按 §7 自行落地（自建形态）。
- 成本略高于裸 CVM，但可预算，且远低于自建高可用的人力与 Supabase 的不确定用量成本。
- 迁移自由度不变：标准 PG，`pg_dump` / 逻辑复制随时可迁；无平台锁定。
- 需要做的：选定云托管实例规格与内网连通、开启自动备份 + PITR、配置异机副本、执行一次恢复演练（§7 第 5 步）。
- 仍是上线阻塞项：**备份 / PITR 未验证前不得上线**；云托管形态可跳过手写脚本，但恢复演练不可省。
