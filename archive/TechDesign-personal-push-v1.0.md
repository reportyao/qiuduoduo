# 技术设计：私人助理感 · 赛后主动触达体系 v1.0

| 项目 | 内容 |
|---|---|
| 范围 | 赛果推送、个性化复盘、专属感功能族的技术实现与成本 |
| 基准 | 100 万注册 / 20 万 DAU 终态 |
| 结论 | **工程量 2–3 周（v1），运行成本 <¥500/月（10 万 DAU）** |
| 前提 | 复用已有：settle 管道、bets.legs、归因三分类、narrate 白名单、PostHog/Novu |

---

## 一、核心认知：专属感 = 个性化渲染，不是个性化计算

直觉错误：100 万人 → 100 万次 LLM 调用。
正确架构：**每一场比赛的分析只算一次（全局事实层），每个用户只做「槽位填充」（免费）**。

```
┌─ 事实层（每场一次，结算时算好）──────────────────┐
│ match_facts: 比分/时间线/归因类/封存概率/收盘概率    │
│ what-if 矩阵: 去掉第 k 腿的结果（N≤4，穷举）        │
│ 死因: 三关哪一关、哪条腿杀死了串关                  │
└──────────────┬───────────────────────┘
               ▼
┌─ 渲染层（每用户，纯模板，成本≈0）─────────────────┐
│ 消息 = 模板 + 用户槽位（他的注、他的金额、他的历史）  │
│ persona 语气 + 数字白名单校验                       │
└──────────────┬───────────────────────┘
               ▼
┌─ 触达层（队列 + 频控）────────────────────────────┐
│ 消息先落库（流内可见）→ 推送只是送达通道              │
│ 去重键 (user, match, event) · 静默时段 · 频次上限    │
└──────────────────────────────────────────────────┘
```

**消息先写进流，推送只是敲门。** 用户关了推送，流里照样有——这是降级底线。

---

## 二、两级推送时序（情绪窗口）

赛后用户的情绪有两条时间线，用两个不同的消息接住：

| 级 | 时点 | 内容 | 数据源 | 语气 |
|---|---|---|---|---|
| **快讯** | T+2min（终场哨） | "终场 1-1。" 只报事实，**不结算不归因** | 实时比分源（API-Football live，已在采购清单） | 中性 |
| **结算** | T+2h（竞彩官方结算） | "结算了：让球主胜没过。这属于随机波动，判断没错。这一注 CLV +1.2。" | settle 管道 + match_facts | persona 语气 |

为什么分两级：终场后 5 分钟是用户最想立刻知道的时刻（他会在别处看比分），先给事实；归因需要结算数据，晚点给反而显得「它想清楚了才说话」。

## 三、消息类型与触发矩阵

| # | 消息 | 触发 | 个性化槽位 | 渲染 |
|---|---|---|---|---|
| 1 | **终场（实况卡终态 + 唯一一次比赛推送）** | T+2min | 他的注状态 | 卡片状态 + 模板 |
| 2 | 结算通知 | T+2h | 他的玩法/结果/CLV/归因类 | 模板 |
| 3 | **串关死因** | T+2h | "死在第 2 关拜仁；前两关都对了" | 模板 + what-if 矩阵 |
| 4 | 连败关切 | 连败 ≥3 | 连败次数/归因占比/今天的决定 | 模板 |
| 5 | 预算事件 | 80%/100%/追损 | 他的预算/他的历史 | 模板（已有） |
| 6 | **专属早报** | 用户本地 T-3h（关注联赛最早停售） | 关注联赛今天 n 场、过闸 m 场、引用记忆 | 模板 |
| 7 | 买后安抚 | 买了后 1h 未关 App | "中间不用再看了" | 静态 |
| 8 | 月度私报 | 每月 1 日 | 全月聚合 | 模板 + 分享卡 |
| 9 | **年度账单 Wrapped** | 年底/大赛后 | 全年聚合 | 模板 + 分享卡 |
| 10 | 按需追问回复 | 用户点卡片追问 | 会话上下文 | **LLM 按需**（唯一用 AI 的地方） |

关键：**1–9 全部是模板+槽位，只有 10 是实时 LLM。**

## 四、LLM 的正确用法：批量变体，不逐条生成

```python
# 每晚批跑一次（几十次调用，不是几十万次）
for template in templates:            # ~10 个模板
    for match in tonight_matches:      # ~30 场
        variants = llm(                # ×10 个语气变体
            PROMPT[locale], facts=match_facts[match], temperature=0.7
        )
        cache[(template, match)] = variants   # 数字白名单校验后入库

# 用户触达时：渲染 = 选变体（按 user_id 哈希取）+ 填他的槽位
msg = cache[(template, match)][user_id % 10].format(**user_slots)
```

- 同一晚看同一场的两个人，拿到不同措辞但同一事实——**专属感的「话」来自变体池，「料」来自他的注**
- 校验：输出数字必须 ⊆ match_facts 白名单；不合格丢弃重试，兜底用纯模板

## 五、数据模型增量（在 v1.1 schema 上）

```sql
CREATE TABLE match_facts (           -- 每场一份，settle 时生成
  match_id TEXT PRIMARY KEY,
  score TEXT, timeline JSONB,        -- 进球分钟/红牌等关键事件
  attribution TEXT,                  -- info_gap/model_bias/variance
  sealed_prob NUMERIC, closing_prob NUMERIC, clv NUMERIC,
  dead_gate TEXT,                    -- 避雷场：死在哪一关
  whatif JSONB,                      -- {legs_signature: {removed_k: payout}}
  facts_hash TEXT
);
CREATE TABLE messages (              -- 消息即流内容，先落库
  id BIGSERIAL PRIMARY KEY,
  user_id UUID, kind TEXT,           -- flash/settle/deadwhy/care/daily/...
  match_id TEXT NULL, payload JSONB, -- 槽位与渲染结果
  locale TEXT, created_at TIMESTAMPTZ,
  read_at TIMESTAMPTZ, pushed_at TIMESTAMPTZ
) PARTITION BY RANGE (created_at);   -- 月分区
CREATE UNIQUE INDEX ON messages (user_id, kind, match_id);  -- 天然去重
```

扇出查询：`SELECT user_id FROM bets WHERE match_id=? AND settled IS NULL` → 逐条渲染入 messages → 推送 worker 按频控批量发。10 万用户 ≈ 数万行插入 + 数万条推送，几分钟内完成，普通 worker 就够。

## 六、成本账（关键数字）

| 项 | 1 万 DAU | 10 万 DAU | 100 万 DAU |
|---|---|---|---|
| 事实层计算 | 0（随 settle） | 0 | 0 |
| 模板渲染 | ≈0 | ≈0 | ≈0（CPU 毫秒级） |
| LLM 批量变体 | ¥10/月 | ¥50/月 | ¥500/月（大赛峰值 ×5） |
| LLM 按需对话（约 3% 日活问 1 次） | ¥60/月 | ¥600/月 | ¥6,000/月（可分级限流） |
| 实时比分源 | 已有采购 | 已有 | 已有 |
| 推送通道 | 0（免费额度） | ¥0–500/月 | ¥1–3K/月（或自接厂商通道归零） |
| 存储增量 | ~1 GB/月 | ~10 GB/月 | ~100 GB/月（月分区+冷归档） |
| **合计增量** | **≈¥100/月** | **≈¥1K/月** | **≈¥8–10K/月** |

对照：100 万 DAU 的这条专属感体系，月成本 ≈ 一名实习生工资的零头。**贵的是第一次搭建的工程时间，不是运行。**

## 七、真正难的三件事（都在工程时间，不在钱）

| # | 难点 | 说明 | 对策 |
|---|---|---|---|
| 1 | **归因必须是真的** | "死在第 2 关"说错一次，专属感秒变欺骗感 | legs 在封存时已固化；结算逐腿判定；what-if 穷举预计算；消息数字 100% 来自 match_facts |
| 2 | **快讯比分源稳定性** | T+2min 推送依赖实时比分 | API-Football live + 双源校验；拿不到就只发结算级，宁慢勿错 |
| 3 | **克制（产品纪律）** | 主动消息超量 = 关通知 = 全线崩 | 每日主动 ≤2 条硬上限（追人层）；频控在触达层统一执行；类型级 opt-out |

## 八、专属感阶梯（产品视角）

| 级 | 感受 | 例 | 实现成本 |
|---|---|---|---|
| L1 | 计分板 | "终场 1-1" | 免费 |
| L2 | 服务 | "你买的没过——1-1 平局。随机波动，判断没错" | 模板 |
| L3 | 朋友 | "连错 3 场了。今天没有值得买的，歇一天" | 规则（数据已有） |
| L4 | 它记得你 | "你说过只买 50——这单 80，我记着呢" | 记忆系统（已有） |
| L5 | 关系 | 年度账单：你的 214 注、最惨一夜、你对得最多的联赛 | 聚合 + 分享卡 |

L1–L4 全部便宜；**L5（Wrapped 式年度账单）是病毒传播装置**——人们晒的不是战绩，是「它懂我的一年」。成本：聚合查询 + 一张分享卡，1 周开发，卡上带账本二维码（合规：晒的是事实与成本，不是推荐）。

## 十、实况卡：状态进卡片，事件进流（v1.1 修订）

**原则：状态变化原地更新，永不追加消息。** 一场比赛从开赛到结算，流里只有一张卡。用户买了或关注某场 → 流内生成一张实况卡：

- **数据**：进球/红牌/点球/半场等事件由实时比分源写入 `match_facts.timeline`（追加）
- **更新机制**：卡片可见期间 30s 轮询 + 关键事件静默推送（content-available，无感知唤醒刷新）；**静默推送不计入用户频控、不出现在锁屏**
- **推送默认矩阵**：开赛/进球/红牌/半场 → 只更新卡片；终场 → 卡片终态 + 该场唯一一次推送；结算+归因 → 第二条消息（两级时序照旧）
- **用户可选**：对单场打开「进球提醒」，仅该场生效、终场后自动过期
- **与消息表关系**：实况卡**不是 messages 行**，是 `match_facts + user_bets` 的视图组件；原「快讯比分」消息类型取消，由卡片终态承担
- **与投注状态联动**：卡片内实时计算「你的注现在赢/走/输」（让球盘按当前净胜球），让-1 在 1-0 时显示"走盘中（本金暂退）"——过程本身就是让球教学
- **克制的可感知化**：卡内公示「本场更新 N 次，只推送了 1 次」——把克制做成看得见的产品态度

流的三分法定稿：**状态 → 卡片（原地更新）；事件 → 流（追加）；对话 → 底部入口。** 三者永不混用。
