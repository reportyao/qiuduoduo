## 一、总体判断

1. **产品机制层（三道闸/封存/归因/账本）经得起审查**，是文档最扎实的部分，未发现结构性缺陷。
2. **触达策略存在根本性错误**：整个 v2.0 以来的"助理主动说话"建立在微信模板消息可日推的假设上，该假设在 2026 年的微信生态**不成立**。这是本次审查最大的发现（P0-1）。
3. **技术文档是"5 千用户架构写了 100 万用户的目标"**：单机 compose、无分区、无幂等、无数据驻留、无 AI 开发规范。补齐后仍然成立——问题不在选型错误，在缺规模路径。

## 三、P0 详述

### P0-1 触达策略根本性错误

**问题**：PRD 通篇假设"每日 19:00 主动推送判决"。CN 主通道指向微信服务号模板消息。

**事实**（2026 年现状）：
- 服务号模板消息处于下线通道，替代品**订阅消息**为"一次授权收一条"，长期订阅类目仅限政务/医疗/交通等公共服务业——**博彩数据分析不在类目内**
- 意味着：日推在微信内**无法规模化**，逐条求授权的产品等于没有推送
- 短信 ¥0.045/条，10 万日活日推 = ¥13.5 万/月，不可行

**影响**：v2.0 以来"助理主动说话"的 AI 原生核心、留存模型、WAV 指标全部依赖触达。

**修复**（→ PRD v4.1 §7 重写）：
1. 触达分层：**关键事件**（预算拦截/连败保护）走能做到的通道；**每日判决**改为"拉取为主 + 轻推为辅"
2. CN 通道矩阵：企业微信（1v1/群，可日发）+ 站内 + PWA 桌面快捷方式 + 短信（仅付费用户关键事件）
3. 核心机制改为**习惯养成**：北极星新增"习惯打开率"（19:00±1h 主动打开占比），引导桌面快捷方式/每日签到式轻锚点
4. Global：Web Push（PWA）+ Email 无此限制
5. 原"每日推送 ≤4 条"修正为"每日主动触达 ≤2 条 + 站内不限"

### P0-2 无规模路径

**修复**（→ TechSpec v1.1 §2）：四级架构阶梯（单机→双机→K8s→多区域），配**规模触发器表**——DAU>5K 上 PgBouncer+读副本；DAU>30K 上 K8s+Kafka；事件>500万/天迁 ClickHouse；LLM 月费>¥5K 启动分层审计。原则：**不为 100 万设计第一天，但每一步有明确的升级条件**。

### P0-3 PIPL 数据驻留

**问题**：全球版只有一套部署。PIPL 要求 CN 用户个人信息境内存储；GDPR 要求欧盟用户数据可说明流向。
**修复**：双栈部署——CN 栈（境内云+ICP）与 Global 栈（EU/US），账号不互通，`users.data_region` 落库时定区。架构图与 API 网关按域名分流。

### P0-4 数据模型 bug：matches.market

**问题**：`matches.market TEXT`——同一场英超在竞彩和国际市场是**两套行情、同一场比赛**，现行设计会导致同一场比赛生成两个 match_id，四价对齐（跨市场比对）在数据层就断了。
**修复**（→ TechSpec v1.1 §6）：
- `matches` 删除 market 字段，match_id 全局唯一（league+date+teams）
- 行情差异全部落在 `odds_snapshots.source/market`
- 新增 `market_availability(match_id, market, official_no, single_allowed, sale_close_utc, official_handicap)`——竞彩特有的单关/停售/让球数挂这里
- 这是四价对齐、跨市场套利分析的前提修正

### P0-5 账本不可篡改无技术支撑

**问题**：append-only 只是纪律，有库权限即可改。产品最大的信任主张（"赛前封存不可改"）目前是空话。
**修复**：`audit_log` 与 `verdicts` 加 `prev_hash` 构成哈希链；每日 job 把账本根哈希 commit 到公开 GitHub 仓库（带平台时间戳，零成本第三方锚定）。任何篡改导致链断裂即被发现。

### P0-6 CN 收单主体

**问题**：微信支付/支付宝收单需企业主体与类目资质，个人主体不可。M1.5 的收入排期隐含此依赖却未标注。
**修复**：Roadmap 中列为 v1.5 硬依赖，提前 4–6 周办主体（个体户/有限公司）+ 类目报备；未就绪前 v1.0 内测不收款。

### P0-7 幂等缺失

**修复**：全链路幂等键规范——支付 webhook（`event_id` 去重）、`POST /react` 与票单（客户端 UUID）、验证码（`purpose+identifier` 限频即幂等）、结算 job（verdict_id 唯一约束）。TechSpec §11 落地。

### P0-8 AI 开发无工程规范

**问题**："全部用 AI 开发"意味着：上下文管理、可验证性、防幻觉改码是第一级工程问题，文档只字未提。
**修复**（→ TechSpec v1.1 新增 §12 整章）：
- 单一事实源：OpenAPI → 双端 codegen；类型严格模式零容忍
- 契约测试先行 + golden dataset 入库（对齐层/模型层各一套）
- 每模块 AGENTS.md 作为 AI 上下文；架构决策 ADR
- **人工把关清单**（AI 不得自主合并）：支付回调/自排除逻辑/封存哈希/权限中间件/密钥与迁移
- CI 门禁：覆盖率、lint 零警告、禁用词扫描（合规）、伪本地化、契约快照

## 五、容量模型（本次审查补算，两文档引用）

| 场景 | 假设 | 结论 |
|---|---|---|
| 注册/DAU | 100 万注册 → DAU 15–20 万（15–20%） | 合理保守 |
| 晚高峰在线 | DAU×10% ≈ 1.5–2 万同时在线（19:00–22:00） | |
| 判决流 QPS | 2 万在线，人均 1 页/60s ≈ 峰值 700 rps | 公开部分 CDN 吸收 90%+，源站 <100 rps，**双机即可扛** |
| 19:00 推送 | 10 万触达 30 分钟 = 56/s | 分桶+队列 worker×4，无压力 |
| odds_snapshots | 5 联赛 ≈ 1000 万行/年；30 联赛 ≈ 8000 万行/年 | 分区+归档必要 |
| LLM | 判决叙述按场次×locale 缓存（命中>90%）；chat 1 万轮/日 ≈ 2 千万 token/日 | flash 级 ¥几十/日，可控 |
